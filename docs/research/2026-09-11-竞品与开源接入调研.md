# AI 短剧/视频创作工作台：竞品、自研与开源接入调研

调研日期：2026-09-11。范围是当前 `tapnow-base` 可执行代码、公开可访问的竞品官方资料与开源仓库。本文覆盖自主研发、商业 API、开源改造和混合路线；是路线建议，不代表已实现，也不直接接入任何依赖。

## 结论

当前项目已经不是只有画布原型：有图像、多模型视频、异步视频任务创建/浏览器轮询、TTS、角色/场景/道具资产、子画布、3D 导演台嵌入和项目导入导出。它的主要缺口是把这些点状能力变成团队可交付的“剧集生产系统”：来源与版权、剧本到镜头、角色资产锁定、可恢复队列、成片时间线、版本协作、真实成本与权限。

开源不是功能优先级门槛。最值得自研的是短剧生产的业务数据、规则和交互闭环；底层生成模型继续通过已接或商业 API 调用，开源项目只补队列、字幕、导出和协作等通用能力，不暗示从零训练视频模型。

第一阶段不应重做画布，先完成“短剧单镜头可追溯、可恢复、可审核、可交付”的最小闭环；其后优先自研分镜联动、资产一致性、参考拉片、take 返工和导演台回写，最后再做实时协作、Agent 和插件生态。

### 最值得自主研发的 5 项

| 自研能力 | 为什么优先 | 产品边界 |
|---|---|---|
| 分镜生产台账与联动失效更新 | 把剧本、台词、配音、字幕、镜头和 take 放入同一条可追溯链，是短剧团队返工效率的核心。 | 台词变更只标记关联项“待更新”，用户逐项确认；保留旧版本，不自动覆盖成片。 |
| 角色/场景资产包与生成前一致性检查 | 用户需要复用可解释的角色、服装、场景和声线规则。 | 管理引用、版本和规则并在提交前检查缺失；不承诺模型输出绝对一致。 |
| 参考视频到可编辑分镜/生成配置 | 把“看过参考”变成可执行的镜头结构，直接缩短前期拆解。 | 提取和人工校正构图、时长、镜头运动等结构；不声称一键精确复刻参考片。 |
| 同镜多 take 对比与局部返工 | 生成式视频的常态是筛选和局部修正，需避免覆盖有效素材。 | 用供应商的生成/编辑能力，本项目自研 take 血缘、A/B 比较、蒙版/锚点编排和回滚。 |
| 3D 导演台参数回写 | 当前已有 3D 预演和截图回传，映射到镜头可形成差异化控制层。 | 复用现有导演台，不重建 3D 引擎；把机位、FOV、轨迹、截图等映射为可编辑镜头/模型参数。 |

## 方法和证据边界

- **已实现**只依据当前仓库源码；界面中的演示数据、文档设想和配置矩阵不等同于生产可用。
- **竞品已确认**只引用公开官方页可读内容；登录后的能力没有公开证据时一律标为未知。
- **实现路线**分为开源改造、商业 API、自主研发和混合。自主研发表示本项目拥有核心业务数据、规则、流程和交互逻辑；它仍可调用开源库或商业 API，不等同于从零训练底层生成模型。
- **开源候选**在本次调研中核验仓库、许可证和公开可用性；第三方模型、权重、插件及数据集仍须在接入前逐项复核许可与维护节奏。

| **批量生成编排与可解释挑选【混合：自研 + 商业 API】** | 一场 12 镜需要按预算批量生成，团队先筛出可审镜头。 | 视频 API 可多任务创建，节点有 `isLoading/outputArtifacts`；无持久队列与批量组。 | 批次可暂停/重试/限额；按镜头展示候选，人工通过/淘汰；规则仅提示如时长、画幅、引用缺失。 | 自研任务编排/批次看板/可解释规则；商业 API 执行；M。 | 不声称“客观自动选最佳”；质量评分先作为人审辅助。 |
| **模型选择与成本预测【混合：自研 + 商业 API】** | 制片按镜头类型、时长、预算选择合适模型，避免试错后才发现超额。 | 有能力矩阵、`creditEstimate/creditStatus`；额度 UI 是 mock。 | 提交前展示已验证模型、约束、估算和预算提醒；完成后记录实际供应商返回用量（若提供）。 | 自研策略、价格版本和预算规则；商业 API/合同价提供成本事实；S–M。 | 未验证模型不显示为“可用”；预测不能替代财务对账。 |
| **版本审阅与交付包【自主研发 + 开源改造】** | 导演、制片、剪辑确认某个镜头/粗剪版本，并向剪辑工具交接。 | 有项目导入导出、`ShotClip`；缺不可变版本、评论、交付 manifest。 | 帧/镜头评论、通过/返工、只读交付版本；导出镜头表、素材清单与 OTIO/EDL 草稿。 | 自研版本/评论/交付数据；OpenTimelineIO/FFmpeg 用于格式转换；M。 | 先交接元数据与素材清单，非一开始自研完整 NLE。 |
| **工作流模板与受控插件机制【自主研发 + 开源可选】** | 新成员按“短剧对白镜头”“商品广告”等模板完成同一流程，团队安装内部能力。 | 节点类型和画布已有；无模板版本、权限、输入输出 schema。 | 模板一键创建节点/默认参数；插件声明权限与 schema；失败不影响主画布。 | 自研 manifest、模板实例化、权限/审批壳；开源库仅按需使用；M。 | 第一批只开放官方内部插件，禁止任意代码注入。 |
| **项目上下文 Agent【混合：自研 + 商业 LLM API】** | 用户上传剧本、参考和资产后，让 Agent 先提镜头计划、预算和待确认问题。 | 文本节点、资产/画布节点和多模型后端已有；无可审计的项目上下文和计划执行器。 | Agent 显示引用来源、计划、成本提示和等待点；用户批准后才创建草稿/任务。 | 自研上下文装配、引用、权限和批准流；LLM 通过商业 API；M。 | 不是自动导演；不直接改生产数据或绕过用户批准。 |

### 不建议直接嵌入：ComfyUI

[ComfyUI](https://github.com/Comfy-Org/ComfyUI) 是成熟的图像/视频扩散图与 API 后端，公开仓库显示 GPL-3.0、API/节点架构和大量维护活动。它适合先作为隔离的可选计算服务，由本项目插件适配器提交固定工作流、接收结果；不建议未经许可证评估就复制其前端或代码到专有应用。同一衍生程序的分发通常须满足 GPL 条件；独立部署本身并不能自动排除许可义务，具体边界、custom nodes、模型权重和分发方式均应由法务复核。接入时固定镜像、白名单 custom nodes、隔离租户，并限制网络/文件系统权限。

## 与现有 Cloudflare Workers 的部署取舍

| 路线 | 新增运行环境 | 适用范围 | 优点 | 边界 |
|---|---|---|---|---|
| Workers 原生先行 | Cloudflare Queues、Durable Objects、D1、R2（保持现有 Workers 部署） | P0 项目/媒体元数据、异步调度、状态查询与小型后台任务。 | 运维增量低，和现有 `functions/api`/R2 路径一致。 | 长时间视频渲染、GPU ASR、部分供应商长轮询仍应交给外部 worker。 |
| BullMQ | 独立 Node.js worker + Redis/Valkey + 数据库 | 重试、优先级、限流、复杂任务依赖。 | 成熟任务模型，适配视频多步骤管线。 | 不能直接运行在 Workers；需要独立部署、监控与 Redis 运维。 |
| LiteLLM | 独立 Python/容器服务，生产常配数据库/缓存。 | 文本/图像/音频模型统一网关、成本、路由。 | 减少供应商协议散落在前端/Workers。 | MIT 仅覆盖开源核心，企业功能另有许可；异步视频仍需任务 facade。 |
| WhisperX + FFmpeg | 独立 Python GPU worker + CPU 渲染 worker + 对象存储。 | 字幕对齐、说话人分离、转码和粗剪导出。 | 直接补齐短剧交付链。 | 不适合 Workers；GPU 成本、中文评测和模型/二进制许可须独立验收。 |

推荐顺序：先采用 Workers 原生路线把 P0 跑通；任务复杂度或吞吐量达到证据阈值后再引入 BullMQ；字幕/拉片/导出以独立 worker 插件接入；LiteLLM 先做有限模型 gateway PoC。这样不把“接开源”误当成当前 MVP 的强制基础设施替换。

## 建议的插件边界

插件不是直接执行任意代码。每个插件应声明：`id/version`、输入输出 JSON Schema、所需权限（读项目/读资产/写草稿/提交任务/导出）、网络域名白名单、成本计量方式、可取消性与数据保留期。平台将插件动作分为：

1. 读取/分析：可在项目授权范围内运行，写入草稿结果。
2. 写入项目或提交生成：直接执行用户已授权的常规动作；费用超预算时显示变更/预算卡，按策略确认。
3. 常规导出按用户授权直接执行；对外发送、不可恢复删除等额外动作按策略确认并记审计日志。

首批开箱可试插件建议为：字幕/配音对齐、参考视频拉片、参考素材管理、镜头导出到剪辑软件（OTIO/EDL）、工作流模板。第二批再做剧本拆解、角色包生成、模型策略/预算、版权检查和 3D 导演台镜头数据回写；它们都应先通过统一任务中心提交，避免重复建设。

## 分阶段落地

**阶段一：现有链路可靠化。** 先用 Workers 原生的 Queues/Durable Objects/D1/R2 或同等托管能力，保存项目/媒体元数据与任务状态；将现有 video create/poll 适配为幂等、可恢复任务，并明确 mock/失败状态。交付一个“现有画布一镜 → 提交 → 刷新恢复 → 成功或可诊断失败”的闭环；不在此阶段强制引入 BullMQ、完整 RBAC 或财务系统。

**阶段二：优先自研镜头生产能力。** 依次交付分镜台账与联动失效更新、角色/场景资产包与检查、参考拉片到可编辑分镜、同镜 take A/B/局部返工、导演台参数回写。底层生成继续接供应商 API；FFmpeg 等只作为媒体处理组件。验收重点是每镜可追溯、可复核、可回滚，不是自动替人选出“最佳”。

**阶段三：交付效率与平台化。** 上字幕/配音对齐、粗剪和 OTIO/EDL 交接、批量编排、预算提醒、模板/受控插件与项目上下文 Agent；团队实际需要时再引入 Yjs、完整 RBAC/审计和供应商核账。React Flow 只在现有画布性能成为已证实瓶颈时做 PoC。

工期未估算：所需时长取决于团队人数、现有 Cloudflare 资源、供应商接入和真实素材规模，当前没有足够依据给出周数。

## 上线前的硬性验证清单

- 用真实供应商账号对每个“已展示模型”做创建、轮询、失败、超时、取消、重复提交和刷新恢复测试，不依据 UI 配置矩阵声称已支持。
- 对所有生成和上传建立幂等键、输入哈希、provider request id、版本快照和可查询原始错误；错误 UI 保留简短中文原因与可复制原始信息。
- 对对象存储、签名访问、删除/保留策略、版权字段、模型输入是否可用于训练进行安全/法务复核。
- 用 500 节点、1000 素材、多人同时编辑和长视频上传压测；用项目恢复与备份演练验证 RPO/RTO。
- 为每个开源项目锁版本、生成 SBOM、保留许可证与 NOTICE，并复核间接依赖与模型权重许可。
