# 参考图人物识别执行方案（占位版）

> 目标：一次读图同时识别场景、道具、人物，人物按真实比例以「站位 + 姿态占位」创建为可编辑角色对象。
> 本文档自包含，执行者无需历史对话上下文。所有路径相对 `D:\无限画布kc\tapnow-base\`。

---

## 一、目标与范围

### 首版做

- 一次视觉模型调用，同时返回粗布景组件（components）和人物（characters），复用现有 `/api/director-layout` 链路，不增加第二次模型调用。
- 人物创建为现有角色系统的普通角色对象（kind: "character"，ue4-mannequin 素体 + 姿态预设），可选中、可移动、可改姿态、可排走位、可拍跟拍——与手动添加的角色完全同权。
- 人物身高按真实米制创建：草稿内与组件同尺度，随尺度校准等比缩放；应用时按估算身高换算模型缩放，保证「人物不会和沙发一样大」。
- 人物占位信息：位置（接触面中心）、面朝方向、姿态（站/坐/蹲/跪/卧映射到现有姿态预设）、估算身高、置信度；遮挡严重的标记待确认。

### 首版不做

- 不还原照片人物的脸、服装、发型、体型细节（需要人体重建能力，超出占位范围）。
- 不新增模型文件，不引入 GLB/VRM 导入；只用内置素体。
- 不做人物与道具的遮挡/碰撞解算（穿模由用户手动调）。

## 三、数据模型设计

### 3.1 新增 LayoutDraftCharacter（layoutDraft.ts）

```ts
export const LAYOUT_CHARACTER_POSTURES = ["stand", "sit", "crouch", "kneel", "lie", "unknown"] as const;
export type LayoutCharacterPosture = (typeof LAYOUT_CHARACTER_POSTURES)[number];

export const LAYOUT_CHARACTER_MAX_COUNT = 8;

/** 姿态 → 现有姿态预设映射；lie 若无对应预设则映射 stand 并强制 uncertain。 */
export const LAYOUT_POSTURE_TO_POSE_PRESET: Record<LayoutCharacterPosture, string> = {
  stand: "stand",
  sit: "sit",
  crouch: "crouch",
  kneel: "kneel-one",
  lie: "stand", // 若 preset 全表存在躺姿则改映射
  unknown: "stand",
};

export interface LayoutDraftCharacter {
  id: string;
  name: string;
  /** 身体与支撑面的接触中心；Y 即支撑面高度（地面=0，沙发座面≈0.45）。与组件同坐标系同单位。 */
  position: [number, number, number];
  /** 估算身高（与组件同单位；校准后为米）。 */
  height: number;
  rotationYDegrees: number;
  posture: LayoutCharacterPosture;
  /** 体型提示，只决定素体选择：male→mannequin，female→female，unknown→mannequin。 */
  bodyTypeHint: "male" | "female" | "unknown";
  confidence: number;
  uncertain: boolean;
  notes?: string;
  visible: boolean;
}
```

`LayoutDraft` 增加 `characters: LayoutDraftCharacter[]`（必填数组，旧数据读取时默认 `[]`；version 保持 1，新增字段全部向后兼容）。

### 3.2 位置语义（重要，写进 prompt）

position 是「身体与支撑面的接触中心」：站立/蹲姿 = 脚底，坐姿 = 臀部在座面上的投影点（Y 直接给座面高度，≈0.45）。这样角色对象的 transform.position 可以原样使用，坐姿角色自然「坐」在沙发上。

### 3.3 layoutSource 扩展（directorProject.ts）

```ts
layoutSource?: {
  batchId: string;
  draftId: string;
  sourceId: string;
  sourceFileName: string;
  componentId: string;
  category: DirectorLayoutCategory | "character";
  confidence: number;
  uncertain: boolean;
  /** category === "character" 时携带的占位元数据 */
  characterMeta?: {
    posture: LayoutCharacterPosture;
    height: number;
  };
};
```

角色对象同样带 layoutSource（同 batchId），从而自动获得：replace-batch 覆盖、布景调整区归属。代价是 transformLayoutBatch / 对象树 /  inspector 里按 layoutSource 处理的逻辑都要兼容 kind:"character"（见第五节）。

## 四、尺度策略（本方案核心，三层保障）

用户的硬性要求：人物比例按真实图片理解，不能和场景道具一样大。

### 第一层：prompt 把人物变成「活比例尺」

系统提示词中强制：以图中站立成年人物身高 1.7 米为基准估算一切尺寸。人物 height 输出估算身高。这样即使完全没有用户锚定，人物与家具的相对比例也来自同一把尺。

### 第二层：数据结构同尺度 + 校准同步

characters 与 components 同坐标系同单位。`calibrateLayoutDraft` 对 characters 执行与 components 完全相同的 factor 缩放（position 与 height 都乘）。用户锚定「沙发宽 2 米」后，人物按同一因子变成正确米制。

### 第三层：应用时按身高换算模型缩放（绝对值兜底）

`buildLayoutBatch` 为每个 character 生成：

```ts
const scaleFactor = character.height / LAYOUT_CHARACTER_NATIVE_HEIGHT; // 实测常量
transform: {
  position: character.position,          // 接触面中心，直接可用
  rotation: [0, character.rotationYDegrees * Math.PI / 180, 0],
  scale: [scaleFactor, scaleFactor, scaleFactor], // 整体等比
}
```

即使草稿尺度估计整体偏大/偏小，人物身高也是绝对米制。身高在 0.5–2.5 米之外的值在校验层夹紧并标 uncertain。

### 配套校验规则（服务端 + 客户端两份同步）

- characters 缺省允许（纯布景图没有人也合法）；最多 8 个，超出截断并记 issue 警告（不阻断）。
- height：有限数字，0.5 ≤ h ≤ 2.5，否则夹紧到边界 + uncertain=true。
- position：三项有限数，|x|、|z| ≤ 100，y ≥ -1 且 ≤ 5。
- posture 必须在白名单；bodyTypeHint 缺省 "unknown"。
- id 与 components 同命名空间去重（组件 id 前缀如 wall_01，人物建议 char_01，撞号自动加后缀）。
- confidence 0–1；<0.65 自动 uncertain。

## 五、客户端改动明细

### 5.1 layoutDraft.ts

- 新增 3.1 的类型与映射表、`LAYOUT_CHARACTER_MAX_COUNT`。
- `validateLayoutDraftCandidate`：解析 `parsed.characters`（可选数组），逐项规范化（字段兜底、id 清洗去重、范围夹紧），写入返回的 draft。**注意：此函数会重建整个 draft 对象，characters 必须显式透传，否则被静默丢弃。**
- `calibrateLayoutDraft`：characters 的 position/height 与 components 同步乘 factor。
- `buildLayoutBatch`：新增角色对象生成（见第四层代码）；角色颜色用 `LAYOUT_CHARACTER_COLOR`（默认角色蓝 #4F8EF7，与手动添加角色一致；若要多色，从 directorStore 导出 CHARACTER_COLOR_PALETTE 的读取函数或在 schema 层放一份只读常量，二选一，避免循环依赖）。
- 新增导出 `LAYOUT_CHARACTER_NATIVE_HEIGHT`（先按第二节完成实测）。

### 5.2 directorStore.ts

- `applyLayoutDraft`：无需改逻辑（buildLayoutBatch 已含角色）；注意应用后 `selectedObjectIds` 会包含角色 id（保持现状全选即可，属可接受行为）。
- `transformLayoutBatch`（约 2507 行起）：
  - 中心点计算（centerX/centerZ 累加与计数）必须包含批次内角色对象，否则「看向整组」和「整体缩放」不以人物为基准。
  - scale：角色 position 相对中心缩放 + transform.scale 乘 factor。
  - offsetX/offsetZ：角色 position 平移。
  - **snapToGround 跳过 kind === "character" 的对象**（坐姿角色会穿进沙发；站立角色落地由 position.y 保证）。
- `DirectorActions` 接口无需新 action；角色应用后的编辑（姿态/位置/缩放）复用现有 applyPosePreset / updatePoseControl / transform 编辑能力。

在组件 preview 之后渲染角色 preview。首版用轻量占位（与现有 box preview 风格一致，实现风险最低）：

- 一个半透明 capsule（或 box 近似人形：高度 = height，宽深 ≈ 0.45×height）放在 position，按 rotationYDegrees 旋转；颜色用角色蓝；hover/selected 时提高不透明度（复用 getLayoutDraftPreviewStyle 的 pattern，或简单三档 opacity）。
- posture 的视觉区分：sit → 在 position 处加一个扁圆「座面投影」；crouch → 高度 ×0.75；其余不变。
- uncertain 角色用与组件一致的琥珀色自发光（#8a6a1e，intensity 0.18）。
- 全部 preview 挂在同一 `userData HIDE_FROM_VIEWPORT_CAPTURE_KEY` group 下（截图不含预览，保持现有约定）。
- 备选（若执行者评估 ProceduralMannequin 可被 preview group 直接复用且性能可接受）：用真实素体渲染预览。默认走轻量占位，不要为首版扩大风险面。

## 十一、实施记录（已完成）

批次 1–6 均已落地，提交历史见 git log。以下记录与原始方案的实现差异与实测结论，供后续维护者参考。

### 12.1 LAYOUT_CHARACTER_NATIVE_HEIGHT 实测结果 = 1.86

第二节要求"不许猜"。实测做法是复用已有的**视口标签锚点**：默认素体 (rigType "ue4-mannequin") 的标签锚点高度 `getUE4GroundedLabelY("mannequin")` = 2.04，减去标签到头顶的间距常量 `VIEWPORT_OBJECT_LABEL_VERTICAL_GAP` = 0.18，得到素体头顶的真实世界高度 **1.86 米**。

该值没有独立常量可引用，因此在 `layoutDraft.ts` 中显式导出 `LAYOUT_CHARACTER_NATIVE_HEIGHT = 1.86`，并在 `layoutDraft.test.ts` 里加了**同步断言**：一旦有人调整标签锚点或间距，NATIVE_HEIGHT 失效会直接测试报错，而不是悄悄缩放错误。

已知偏差：UE4 模型加载失败回退到程序化素体时实际高度不同，该边缘场景接受偏差（已在常量注释中写明）。

### 12.2 服务端与客户端校验做了不同取舍（对原方案的细化）

原方案要求"两份校验规则一致"。实际实现区分了职责：

- **服务端严格拒绝**（issues → 触发第二次重试纠正）：unknown posture / 非法 height /id 重复 / 超出 8 人 → 全部抛出 issues，让模型有机会自己改对。
- **客户端宽容夹紧**（不阻断）：等同于原有的容错风格，单人数据异常只标记 `uncertain=true`，不丢弃整张草稿。

原因：服务端能看到上一次输出并可重试，严格校验能提升最终质量；客户端面对的是已经无法改变的返回结果，宽容处理对用户体验更好。两边的**白名单和边界值保持一致**（同一组 6 个 posture、0.5–2.5 米身高区间），语义不冲突。

### 12.3 preview store 的选中互斥（原方案未预见的问题）

`layoutDraftPreviewStore` 原本只有 `selectedComponentId`。加入 `selectedCharacterId` 后暴露一个 bug：编辑人物身高 → `setDraft` → 原逻辑发现 `components[0]` 存在且 `selectedComponentId` 为 null → 自动选中第一个组件 → 人物编辑器被替换掉。

修复后的语义：**有组件被选中时人物选中让位；没有任何组件选中时才保留人物选中**。这条是实际调试中发现的，改动集中在 `layoutDraftPreviewStore.ts` 的 `setDraft`。

### 12.4 浏览器冒烟替换为全链路集成测试

仓库 root `node_modules` 里的 playwright 在一次失败的 `npm install` 中被 npm 当作 extraneous 包剪掉了，且当前环境无法联网重装（npm 官方源与 npmmirror 均不可达），因此第八节的浏览器冒烟**未能执行**。

替代方案：新增 `src/editor/schema/layoutDraftPipeline.test.ts`，在 vitest 里走完整链路——模拟模型返回 JSON → 客户端解析 → 尺度锚定校准 → buildLayoutBatch → 应用进 directorStore → transformLayoutBatch。其中两个用例直接对应用户的核心诉求：

- **相对比例守恒**：锚定沙发 2 米后，人物身高/沙发宽的比值与校准前一致。
- **绝对米制兜底**：`scaleFactor × NATIVE_HEIGHT` 必须等于校准后的身高数值。

另有三个用例覆盖向后兼容（无人物）、角色与组件同权（6 个对象 = 4 布景 + 2 人物）、以及"整批贴地不会把坐姿人物拉下沙发"。

**遗留**：浏览器冒烟与"亲眼目测比例"的人工验收需要用户在有 playwright 的机器上执行 `npm install --save-dev playwright@1.60.0` 后补做，或直接在实际参考图上端到端验证。

### 12.5 验证结果

- vitest（导演台全量）：741 → 746 通过（88 文件）。
- `tsc -b`（director-desk）：通过。根 tsconfig 的历史错误（测试文件缺 vitest 全局类型、ErrorBoundary 等）与本次改动无关，未触碰。
- 双端 `vite build`：director-desk 与主应用均构建成功。

## 十二、风险与注意事项

- **NATIVE_HEIGHT 未实测前不要写死 1.8**：Mixamo 管线是 1.8，程序化素体必须实测；猜错会整体缩放错误。
- **两份校验必须同步**：server.mjs 与 layoutDraft.ts 各有一份；只改一份会导致客户端把 characters 剥掉（validate 重建对象）或服务端放行非法数据。
- **旧数据兼容**：localStorage 里已有项目的 layoutBatches/objects 没有角色字段；所有读取处默认空/跳过，不要假设存在。
- **transformLayoutBatch 的 snapToGround**：加角色后最容易踩的坑是坐姿角色被贴到地面穿进沙发——已设计为跳过 kind:"character"，实现时注意该函数内多个分支（scale/offset/snap）都过一遍。
- **循环依赖**：schema 层（layoutDraft.ts）不能 import directorStore；角色调色板需要导出常量或放只读副本。
- **lie 姿态**：先读 MANNEQUIN_POSE_PRESETS 全表确认有无躺姿；没有就映射 stand + uncertain，并在 notes 提示「卧姿需手动调整」。
- **人物数量上限 8**：prompt 和校验双重限制，超出截断而非报错（布景 30 个组件的既有风格是报错，人物选择截断是因为「多识别几个人」比「整个人物任务失败」体验好；如团队倾向一致也可改为报错，任选其一，在 PR 描述里注明）。
- **性能**：preview 用轻量占位（ capsule/box ），不要引入真实素体到预览 group，避免拖慢暂存预览。
- **部署站模型额度**：本地 .env 当前走 DeepSeek 端点（MIMO_BASE_URL=https://api.deepseek.com/v1，MIMO_VISION_MODEL_ID=deepseek-flash），冒烟前确认额度；部署站若要可用需先做第七节。
